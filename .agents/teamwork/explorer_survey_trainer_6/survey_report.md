  - Clicking "🔑 Войти по коду из Telegram бота" sets `tgCodeStep = 1` and opens `showTgCodeDialog`.

  1. Open dialog -> Show single 6-digit PIN input field with 5-minute countdown (300s).

### Focus Area 2: 1-Click Telegram Login Button (`tg://resolve`)

#### Relevant Files
- `app/src/main/java/com/trainerapp/pro/ui/screens/TrainerAuthScreen.kt` (lines 138–186)
- `app/src/main/java/com/trainerapp/pro/data/auth/TrainerRemoteAuthManager.kt` (lines 521–542, 545–601)

#### Current Implementation
- In `TrainerAuthScreen.kt`:
  - When the user taps "✈ Войти через Telegram (в 1 клик)", it calls:
    ```kotlin
    val session = viewModel.remoteAuthManager.initTelegramSession()
    val targetUrl = if (session != null) session.second else "https://t.me/fitnessecosystemBOT?start=login"
    try {
        val intent = Intent(Intent.ACTION_VIEW, Uri.parse(targetUrl))
        context.startActivity(intent)
    } catch (_: Exception) {}
    ```
  - It then starts a coroutine polling loop:
    `viewModel.remoteAuthManager.pollTelegramSession(sessionId)` every 1500ms up to 300 seconds.
- In `TrainerRemoteAuthManager.kt`:
  - `initTelegramSession()` sends `{}` (empty JSON) to `POST /api/auth/telegram/session-init`.
  - On the backend (`server.js` line 746):
    `const requestedRole = (body && body.requestedRole === 'trainer') ? 'trainer' : 'athlete';`
    Since `{}` was sent, `requestedRole` was evaluated as `'athlete'` instead of `'trainer'`!

#### Gap Against Requirement R2
- The requirement mandates:
  > *"1-click Telegram button must trigger `tg://resolve?domain=fitnessecosystemBOT&start=auth_<sessionId>` with fallback and poll session token."*
- Currently, `TrainerAuthScreen.kt` attempts only `https://t.me/...` HTTP URL. On many Android configurations, this causes Chrome/browser to open rather than directly invoking Telegram.
- Missing `tg://resolve?domain=fitnessecosystemBOT&start=$sessionId` scheme intent invocation with fallback to `https://t.me/...`.
- `initTelegramSession()` does not specify `requestedRole = "trainer"`, which can cause role mismatches if a new trainer account is provisioned via the bot.

  - `GoogleDriveSyncManager.validateAndProcessPairingData` verifies PIN in cloud `pairing` map, enforces 5-minute TTL, checks for single-use (`PAIRED`/`USED`), and creates/updates `ClientEntity`.
- **Photo / Avatar**:

  - Athlete avatar (`avatarBase64`) is extracted and persisted into `ClientEntity.avatarBase64`.
- **Restrictions**:

   - The Web Portal (`cloudSync.js` line 131) and Telegram Bot register athlete contraindications in the cloud pairing record under `"restrictions"`.
   - Result: Athlete restrictions set via Web or Telegram Bot were dropped when the Trainer paired the athlete.
2. In `GoogleDriveSyncManager.kt` (line 297–306):
   - When updating an existing client during pairing, `notes` was only updated if `client.notes.isBlank()`. If an athlete updated their restrictions/injuries on the Web, the changes did not propagate.
