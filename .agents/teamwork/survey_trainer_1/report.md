### 2.3. Привязка атлета по 6-значному PIN и QR-коду (`HomeScreen.kt` & `GoogleDriveSyncManager.kt`)
- **Ввод кода**:
  - Плейсхолдер: `"739102 (без тире)"`.
  - Вспомогательная функция `extractPairingCode(input)`:
    - Автоматически вырезает дефисы, пробелы и посторонние символы (`filter { it.isDigit() }`).
    - Автоматически парсит URL ссылки вида `https://fitnessapp.pro/pair?code=265507`, `?pin=265507` или `/pair/265507`.
    - Автоматически извлекает 6-значный код из JSON QR-пейлоада (`{"pin":"265507"}`).
- **Сканирование камерой**:
  - Рантайм-запрос разрешения: `rememberLauncherForActivityResult(ActivityResultContracts.RequestPermission())` с проверкой `ContextCompat.checkSelfPermission(context, Manifest.permission.CAMERA)`.
  - При предоставлении разрешения запускается `cameraLauncher.launch(null)` (`TakePicturePreview`).
  - Дополнительная кнопка «Из фото QR» для выбора изображения из галереи (`ActivityResultContracts.GetContent()`).
- **Защита от сбоев в `QrCodeScannerHelper.kt`**:
  - Обработка `Throwable` (включая `OutOfMemoryError`).
  - Автоматическое масштабирование входящих битмапов с ограничением максимальной стороны в 800 пикселей (`MAX_SCAN_DIMENSION = 800`).
  - Оптимизация памяти при чтении из Uri: декодирование с `inSampleSize` и конфигурацией `Bitmap.Config.RGB_565`.
  - Явный вызов `scaledBitmap.recycle()` в блоке `finally`.
- **Строгая серверная/облачная валидация (`validateAndProcessPairingData`)**:
  1. *Поиск по коду*: если ключ отсутствует в облачном узле `pairing`, возвращается `IllegalArgumentException("Код не найден")`.
  2. *TTL 5 минут*: проверяется метка времени `timestamp`. Если `System.currentTimeMillis() - timestamp > 5 * 60 * 1000L`, код считается просроченным, возвращается `IllegalStateException("Срок действия кода истёк (действует 5 минут)")`, а просроченная запись удаляется из облака.
  3. *Одноразовость (Single-Use)*: если статус уже `PAIRED` или `USED`, возвращается `IllegalStateException("Этот код уже был использован")`.
  4. *Zero-Mocks валидация*: запрет фиктивных клиентов — проверяется непустой `clientUuid`. Создается или обновляется реальный `ClientEntity` с сохранением в локальной Room SQLite.
  5. *Передача карточки тренера*: в запись сопряжения в облаке записываются `coachName`, `coachPhone`, `coachAvatarBase64` и статус `PAIRED`, благодаря чему приложение атлета сразу отображает данные тренера.

- Ключ шифрования генерируется через SHA-256 хэш мастер-пароля.

## 5. Выявленные дефекты, расхождения и пробелы (Gaps & Findings)

В ходе углубленного анализа кодовой базы выявлены следующие архитектурные и функциональные аспекты:

### 🔴 GAP 1: Отсутствие строки ограничений и травм на экране тренировки (`WorkoutScreen.kt`)
- **Описание**: В модели `ClientEntity` есть поле `notes` (в диалоге настроек подписанное как *«Ограничения / Заметки»*), а на `HomeScreen.kt` оно отображается в карточке атлета. Однако непосредственно на экране составления тренировки (`WorkoutScreen.kt`), где тренер выбирает упражнения и назначает рабочие веса, **строка/плашка с ограничениями и травмами подопечного отсутствует**.
- **Риск**: Тренер может забыть о противопоказаниях подопечного (например, межпозвоночная грыжа, травма плеча) и назначить опасное упражнение.
- **Рекомендация**: Добавить компактную информационную плашку с иконкой `Warning` / `HealthAndSafety` и текстом травм/ограничений подопечного в верхнюю часть `WorkoutScreen.kt` (под заголовком или над лентой упражнений).

### 🔴 GAP 2: Локальная заглушка проверки 2FA OTP (`verify2FaOtp`)
- **Наблюдение**: В `MainViewModel.kt` метод проверки 2FA OTP реализован следующим образом:
  ```kotlin
  fun verify2FaOtp(otp: String): Boolean {
      val clean = otp.filter { it.isDigit() }
      if (clean.length == 6) {
          completeLogin()
          return true
      }
      return false
  }
  ```
- **Проблема**: Проверяется лишь то, что введено ровно 6 цифр. Запрос на серверный эндпоинт `/api/auth/telegram/verify-otp` **не отправляется**! Любой произвольный 6-значный код позволяет авторизоваться при включенном 2FA.
- **Рекомендация**: Реализовать сетевой вызов к `/api/auth/telegram/verify-otp` с передачей `{ username, code }` и выполнять `completeLogin()` строго при получении ответа HTTP 200.

### 🟡 GAP 3: Отсутствие удаленной проверки статуса одобрения (72h Owner Approval)
- **Наблюдение**: Переменная `isApproved` хранится исключительно в локальном `SharedPreferences`. При регистрации отправляется запрос в веб-бэкенд, но приложения не имеют механизма проверки статуса одобрения аккаунта владельцами (`/api/trainer/status` или проверка флага в облаке).
- **Проблема**: Если владелец одобрит тренера на сервере/портале, в мобильном приложении статус не обновится автоматически без ручного вмешательства.
- **Рекомендация**: Добавить при попытке входа легковесный запрос статуса одобрения на бэкенд по логину/телеграму тренера.

### 🟡 GAP 4: Несоответствие версий (v1.0.5 vs v1.0.8)
- **Наблюдение**: В исходном ТЗ R2 требовалось установить версию `versionCode = 5, versionName = "1.0.5"`, однако в последующих follow-up и текущем файле `build.gradle.kts` уже установлены `versionCode = 8, versionName = "1.0.8"`. Облачный манифест в `UpdateService.kt` и `GoogleDriveSyncManager.kt` также ориентирован на `1.0.8`.
- **Рекомендация**: Зафиксировать и согласовать со всеми участниками экосистемы актуальную релизную версию (v1.0.8).
